Root Causes
Problem 1 — No KPI Card Standard
Each page invented its own card style. Some use dark gradients, some use pastel, some use white, some use chips. Result: no visual consistency.
Problem 2 — No Color System Per Module
Colors were assigned page-by-page with no module grouping. Finance pages look nothing like each other.
Problem 3 — Table Headers Vary Wildly
Dark black, dark navy, white with border — each page chose a different table header background, making the data feel unrelated.
Fix 1 — One KPI Card Template
All KPI cards use the same gradient template (module color), same size (padding 12px 16px), same font sizes. Only the color changes per module.
Fix 2 — Module Color System
9 modules, 9 defined colors. Every page belonging to Operations uses #5A32D4. Every Finance page uses #0277bd. Consistent, calm, purposeful.
Fix 3 — One Table Header Style
All table headers use background #f8faff with a bottom border in the module color. Light, clean, and consistent across all 40+ tables.
Module Color Palette
Every page belongs to exactly one module. The module color is used for: KPI card gradient, table header bottom border, filter chip active state, form accent, section titles. Never mix module colors within one page.

Table Layout Standard — Applied to ALL 40+ Tables
Every single data table in the application follows this exact structure top-to-bottom: page header → filter strip → sticky column header → data rows → pagination.
Rule: Structure Order (never deviate)
1. Page title + action button (+ New, + Add, Export)
2. Filter strip (search box + dropdowns + status chips) — always ABOVE column headers
3. Column header row — sticky, never scrolls away (CSS: position:sticky; top:0)
4. Data rows (collapsible if row has detail fields)
5. Pagination row (records count + page buttons)
Rule: Filter Strip Contents
Always include: Search box (leftmost), then dropdown filters, then status chip filters. "Clear" link on the right. The filter strip background is #fff, bottom border 1px #e2e8f0.
Rule: Column Header Styling
background: #f8faff | bottom border: 2px solid [module color at 30% opacity] | font: 9px, uppercase, 700 weight, #64748b | padding: 8px 12px | position: sticky, top: [filter height]
Rule: Long Text / Overflow in Cells
Any cell with potentially long content (description, name, purpose) shows max 1 line truncated with "…". Clicking that row expands a collapsible detail row below it showing the full content. Never let text overflow or wrap awkwardly in the table.

Forms — Multi-Step Wizard Standard
All forms use the banner+wizard pattern. Forms with many fields are split into numbered steps. The step sidebar never scrolls — only the right content area scrolls.
Forms like Invoices and Purchase Orders that have repeating line items use a special Line Item Table component inside one of the steps. This section is flexible in height — it grows as lines are added.

Rule: Line Item Tables
The line item section (Step 2) has no fixed height. It grows naturally as rows are added. The wizard container itself is min-height 60vh and scrolls internally so the step sidebar stays fixed. The "Add Line Item" button is always visible at the bottom of the rows. Each row has a delete (✕) button. The running total updates live.
Collapsible Table Rows — Overflow Standard
When a table row has content that would overflow (long names, notes, multi-field details), the main row shows a truncated preview with an expand arrow. Clicking expands a detail row below it.
When to Use Collapsible Rows
Use when: (a) a text field exceeds 30 characters, (b) a row has sub-items (invoice has line items), (c) a record has status history, (d) a record has attached files or notes. Never show all detail inline — it destroys table readability.

LOI Register — Letters of Intent
Operations Module · Pre-project pipeline tracker
Purpose: Tracks all Letters of Intent received from clients before a formal project starts. An LOI is a document where a client declares their intention to hire Ratal for a project. It is not a signed contract yet. When the LOI is confirmed and a contract signed, it is "Converted" into a full Project in the Projects module.
KPI Cards
CardTypeMeaning
Total LOIsCountTotal number of LOI records ever created, all statuses
Active Pipeline (SAR)SAR ValueSum of estimated value of all LOIs that are currently in active status (received but not yet converted or rejected). Sub-labels show count of received vs responded.
ConvertedCountNumber of LOIs that have been converted into real Projects. This is your win-rate indicator.
Total Est. ValueSAR ValueTotal estimated contract value across ALL LOIs regardless of status. Gives a picture of total business opportunity that came through the door.
Filters
FilterTypeWhat it filters
Search LOI#, client, scope…Text searchSearches across LOI number, client name, and scope/description fields simultaneously
All UnitsDropdownFilter by business unit (TISU, NFSU, ACCSYS etc.) — which Ratal division received the LOI
All StatusesDropdownFilter by status: Received, Responded, Won/Converted, Lost, Cancelled
Table Columns
ColumnTypeMeaning
LOI #Auto IDSystem-generated unique reference number for this LOI (e.g. LOI-2026-001)
Client / ContractorTextThe client company who sent the LOI to Ratal
UnitCodeWhich Ratal business unit this LOI is assigned to (e.g. TISU = Telecom Installation Services Unit)
Est. ValueSARThe estimated contract value as stated in the LOI. May not be the final project value.
DeadlineDateThe deadline by which Ratal must respond to the LOI or submit a proposal
StatusBadgeCurrent stage: Received (new) → Responded → Won (converted) or Lost/Cancelled

Purchase Orders
Finance Module · Incoming (Receivable) & Outgoing (Payable)
Purpose: Manages all purchase orders in both directions. Incoming POs are POs that Ratal receives FROM clients — meaning clients are ordering Ratal's services and will pay Ratal (Receivable). Outgoing POs are POs that Ratal issues TO suppliers/subcontractors — meaning Ratal is buying from them and will pay them (Payable).
KPI Cards (apply to active tab — Incoming or Outgoing)
CardTypeMeaning
Total ValueSARSum of all PO values currently shown (based on active filters). If you filter to Incoming + Active, this shows your active receivables pipeline value.
POs in ViewCountHow many PO records match the current filter. Changes when you apply filters.
With Change OrdersCountHow many POs have had their original value modified by a Change Order (CO). COs adjust scope or price after PO is signed.
Avg PO ValueSARAverage value of POs currently in view (Total Value ÷ POs in View). Helps gauge typical contract size.
Filters
FilterTypeWhat it filters
Tab: Incoming / OutgoingTab switchIncoming = POs received from clients (receivable). Outgoing = POs issued to suppliers (payable). Switches the entire table view.
Status chips: All / Active / Invoiced / Closed / CancelledStatus filterActive = PO in progress; Invoiced = invoice submitted against PO; Closed = fully settled; Cancelled = voided
Search contractor, PO#…Text searchSearches contractor name, PO number, and project code
All DepartmentsDropdownFilter by Ratal internal department responsible for this PO
From / To datesDate rangeFilter by PO date range
Table Columns
ColumnTypeMeaning
DATEDateDate the PO was signed or issued
DEPTBadgeRatal internal department responsible (TISU, NFSU, FINANCE etc.)
CONTRACTORTextFor Incoming: the client company. For Outgoing: the supplier/subcontractor being paid.
CONTRACTOR PO #TextThe PO number as it appears in the contractor's system (not Ratal's internal number)
PROJECTLinkRatal project code this PO is linked to (e.g. P-26001). Clickable to go to that project.
VALUE (SAR)SAROriginal PO value. If changed orders exist, the original + change order total is shown separately.
INVOICEDSAR + %How much has been invoiced against this PO so far. Progress bar shows % invoiced vs total PO value.
STATUSBadgeCurrent PO lifecycle status

Money Requests
Finance Module · Internal fund request workflow
Purpose: Manages the internal process for staff requesting cash/funds to cover project or operational expenses in the field. A staff member submits a Money Request (MR) stating how much they need and why. It goes through approval stages: Department Head → Accounts → Finance → funds are issued and the staff member acknowledges receipt. This replaces informal cash requests and creates a full audit trail.
KPI Cards
CardTypeMeaning
Total Open (SAR)SARTotal value of all money requests that are still open (not yet settled). This is real cash the company has committed or is being asked to commit.
Pending DHCountRequests waiting for Department Head approval. These are the newest and have not started the approval chain yet.
Accts / FinanceCountRequests that have passed DH approval and are now waiting for the Accounts or Finance team to process and issue the funds.
Funds in FieldCountRequests where cash has been issued and is currently held by the requestor in the field. These need to be settled (receipts submitted) to close.
Status Stages (in order)
StatusMeaning
PendingJust submitted. Waiting for DH to review.
DH ApprovedDepartment Head has approved. Now waiting for Accounts.
Accts PendingAccounts team is reviewing the request before funds are issued.
Finance PendingFinance team review (for larger amounts requiring CFO/Finance Manager sign-off).
Funds SentMoney has been sent (bank transfer or prepared for cash issue).
IssuedCash/transfer received and acknowledged by requestor.
Part. IssuedOnly part of the requested amount was issued (partial approval).
DH AcknowledgedDepartment Head has seen and acknowledged the issuance.
DistributingFunds are being distributed to multiple field workers (splitting one MR).
Sent Back by AcctsAccounts returned the request — needs correction or more info from submitter.
Table Columns
ColumnTypeMeaning
MR #Auto IDUnique reference number (e.g. MR-2026-0023). Use this to track the request in all communications.
DATEDateDate the request was submitted
DEPTBadgeThe department the requestor belongs to
PURPOSETextShort description of what the money is for (e.g. "PETTY_CASH_EXP — ANB-77"). Collapsible for full details.
REQUESTEDSARThe amount of money requested
STAGEBadgeCurrent stage in the approval workflow (see status stages above)

Fleet / Vehicles
Operations Module · Vehicle register, assignments, maintenance
Purpose: Manages Ratal's entire vehicle fleet — owned and rented. Tracks vehicle documents (registration, insurance, Istimara), driver assignments, and maintenance logs. The critical function is the expiry tracker — it alerts you when any vehicle document is about to expire, preventing fines from driving with expired documents.

Expiring ≤30dCount (⚠)Vehicles where any document (Istimara, insurance, etc.) expires within 30 days. ACTION REQUIRED — renew before expiry.
Expired DocsCount (🔴)Vehicles with at least one document already expired. URGENT — vehicle should not be driven until renewed.

Field Payment Notifications
Finance Module · ATM card distribution tracker
Purpose: Tracks the distribution of cash/funds to field workers using ATM cards. When a Money Request is approved, the funds are loaded onto assigned ATM cards and distributed to workers. This module records those sessions, monitors that the right amounts were given to the right workers, and flags any over-distribution (giving more than authorized) or proxy distributions (someone receiving funds on behalf of another person).
KPI Cards
CardTypeMeaning
SessionsCountNumber of distribution sessions in the selected month. One session = one batch of fund distributions (could cover multiple workers).
Pending ReviewCount (⚠)Sessions that need a Finance/Accounts officer to review and confirm the distributions were correct
Proxy AlertsCount (⚠)Cases where a person received funds on behalf of someone else. These need verification that the proxy was authorized.
Over-DistCount (🔴)Cases where a worker was given more funds than their approved Money Request authorized. Requires immediate investigation.
Tabs
TabWhat it shows
SessionsList of all distribution sessions with date, amount, and status
Individual LedgerPer-worker view: how much each person received, from which MR, on which date
Card BalanceCurrent balance on each ATM card. Used to check if any card has unspent funds that should be returned.
Filters
FilterWhat it filters
Month (date picker)Show only sessions for this calendar month
All StatusesFilter by session status: Pending Review, Reviewed, Flagged
All CardsFilter to show distributions for one specific ATM card number
All DeptsFilter by department of the workers who received funds
Search submitter / MR #Search by person who submitted the distribution or by Money Request number

Projects
Operations Module · Project register and portfolio tracker
Purpose: The central register of all Ratal projects. Every project has a unique code (P-YYYY-NNN) and is linked to a client, department, POs, invoices, expenses, and employees. The Projects page gives a portfolio-level view of all active and carry-forward work, with financial summaries showing portfolio value and remaining budget.
KPI Cards
CardTypeMeaning
ActiveCountProjects currently in progress (not closed or cancelled)
Carry-fwdCountProjects that were started in a previous year but are still ongoing
Portfolio (SAR)SARTotal contract value of all active projects combined. This is Ratal's total revenue under active contracts.
Remaining (SAR)SARPortfolio value minus what has already been invoiced. This is the remaining billable work left in current contracts.
Filters

RolloverAction button — moves selected projects to the new financial year as carry-forward
Table Columns

CONTRACTORTextThe client/contractor who awarded this project to Ratal
DEPTBadgeRatal's internal department responsible for executing this project

Purpose: The master database of every external organization Ratal does business with. Each party is assigned a unique code (CONT-001, SUP-001, etc.) and type. This master record is referenced by POs, Invoices, Projects, and Accounts entries. You must create a party here before you can reference them anywhere else in the system.

LocalLocal service providers (transport, accommodation etc.). Code prefix: LOC-
RentalsCompanies Ratal rents vehicles or equipment from. Code prefix: REN-

New Invoice Form
Finance Module · 4 steps · Creates a sales invoice from Ratal to a client
Purpose: Creates an official invoice that Ratal sends to a client to request payment for services rendered. The invoice must be linked to a Project and an Incoming PO. The line items describe exactly what work was done and how much it costs. After creation, the invoice goes through an approval workflow before being sent to the client.
Step 1 — Invoice Header
FieldRequired?Explanation
EntityRequiredWhich Ratal legal entity is issuing this invoice (ACCSYS, RAT, GWT). This determines the letterhead, bank account, and VAT number on the invoice.
Invoice DateRequiredThe official date of the invoice. Usually today. This date is what clients use for payment terms (e.g. Net 30 = pay within 30 days of this date).
ProjectRequiredWhich project this invoice is billing for. Pulls the client name automatically.
Purchase OrderRequiredThe client's PO number that authorizes this invoice. Clients will reject invoices not matching their PO.
Invoice ReferenceAutoSystem-generated unique invoice number (e.g. INV-2026-0247). Cannot be manually changed.
Payment TermsRequiredHow many days the client has to pay (Net 30, Net 60, etc.). Affects the due date calculation.
CurrencyRequiredInvoice currency (default SAR). Some international clients use USD.
NotesOptionalAny special notes to print on the invoice (e.g. "Payment via bank transfer only")
Step 2 — Line Items (flexible, grows as you add rows)
FieldRequired?Explanation
DescriptionRequiredWhat service or work was performed. Be specific — clients will review this against their PO scope.
QuantityRequiredNumber of units (could be days, hours, pieces, lump sum=1)
UnitRequiredUnit of measure: Day, Hour, Each, Lump Sum, Month, Meter, etc.
Unit Price (SAR)RequiredPrice per one unit
TotalAuto-calcQuantity × Unit Price. Calculated automatically — cannot be typed directly.
Step 3 — Taxes & Totals
FieldRequired?Explanation
SubtotalAuto-calcSum of all line item totals before tax
VAT (15%)Auto-calc15% VAT applied to the subtotal (mandatory in Saudi Arabia for VAT-registered entities)
DiscountOptionalAny discount agreed with the client. Enter as SAR amount or percentage.
Grand TotalAuto-calcSubtotal + VAT − Discount. This is the amount the client must pay.
Retention (%)OptionalSome contracts hold back a % of payment (retention) until project completion. If applicable, enter % here.
Net PayableAuto-calcGrand Total − Retention amount. The actual amount expected to be paid now.
Step 4 — Attachments
FieldRequired?Explanation
Supporting DocumentsOptionalAttach delivery notes, completion certificates, timesheets, or any documents the client requires with the invoice. All files go to Google Drive (not Supabase).
Internal NotesOptionalInternal notes for Accounts team only — not printed on the invoice. E.g. "Client requested invoice PDF by email, not portal."
